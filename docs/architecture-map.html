Especificaciones Formales de Criptografía para Ethereum

Implementaciones ejecutables de los primitivos criptográficos de Ethereum, escritas en Lean 4 con teoremas formales verificados por máquina. El código se compila también como extensión Python vía bindings C.

La idea central: cada primitivo criptográfico tiene dos caras en este repo. La spec es código ejecutable — se compila, corre, y genera Python bindings. Los teoremas (carpeta Proofs/) verifican propiedades matemáticas de esa spec. Viven en árboles paralelos: Bls/G1.lean define la aritmética, Proofs/Bls/G1Group.lean demuestra que forma un grupo.

Flujo de dependencias

KZG depende de BLS (usa sus puntos de G1 y el pairing). XMSS es independiente: no importa nada de BLS y trae su propio hash, BLAKE2s. Los teoremas observan las specs, pero las specs nunca dependen de los teoremas.

BLS
BLS12-381
Curva elíptica, firmas, pairing
▾

Implementación completa de la curva BLS12-381: aritmética de campos finitos (Fp, Fr, Fp2, Fp6, Fp12), puntos de curva en coordenadas Jacobianas (una forma de guardar los puntos que evita divisiones, que son caras), compresión/descompresión (punto ↔ bytes), hash-to-curve (convertir un mensaje en un punto de la curva), pairing (la operación e(P, Q) que permite verificar; la variante usada se llama optimal Ate), y verificación de firmas BLS según el borrador de estándar del IRTF (draft-irtf-cfrg-bls-signature).

KZG Commitments
Compromisos polinomiales para blobs
▾

Compromisos polinomiales KZG (por sus autores: Kate, Zaverucha y Goldberg) para los blobs del EIP-4844 (proto-danksharding). Usa BLS12-381 como curva subyacente. Incluye FFT sobre Fr, bit-reversal, el trusted setup, y el muestreo de disponibilidad de datos (DAS): celdas con su proof KZG y recuperación de las que falten.

Specs vs. Proofs

El repo separa deliberadamente el código ejecutable de los teoremas. La library EthCryptographySpecs compila a código nativo (y se linkea en la extensión Python). La library Proofs solo contiene teoremas — no genera código, no se linkea.

Spec (ejecutable)

  • Definiciones con def y structure
  • Fp = Fin p — canonicidad por construcción: un Fp nunca puede ser ≥ p
  • Se compila a C vía Lean compiler
  • Python bindings en bindings/
  • Prioriza claridad, no performance

Teoremas (la librería Proofs)

  • Teoremas con theorem
  • uncompress_compress — round-trip (ida y vuelta devuelve el mismo punto)
  • fftField_fftField_inv — la iFFT deshace la FFT
  • Ceremony pairing checks — soundness (nunca acepta un setup inválido)
  • MSM correctness, sqrt soundness (la raíz devuelta es una raíz de verdad)

Cómo se enlazan: ejemplo con Fp.sqrt

El teorema importa la spec y referencia sus funciones por nombre. Si la spec cambia, el teorema deja de compilar.

SPEC — Bls/Fp.lean:79
-- Función que corre. Se compila a C. def sqrt (a : Fp) : Except BlsError Fp := let cand := powNat a ((modulus + 1) / 4) if (cand * cand).beq a then .ok cand else .error .notASquare
PROOF — Proofs/Bls/Compress.lean:32
-- Teorema. No genera código. theorem sqrt_ok {a c : Fp} (h : Fp.sqrt a = .ok c) : (c : ZMod Fp.modulus) * c = a := by rw [Fp.sqrt] at h -- despliega la def split at h · rename_i hbeq cases h exact beq_iff'.mp hbeq · cases h

El mecanismo concreto tiene tres partes:

  1. import (línea 1 del archivo de teoremas) — trae al scope todas las definiciones de la spec.
  2. namespace — el teorema se ubica en EthCryptographySpecs.Bls.Fp, el mismo namespace que la spec.
  3. rw [Fp.sqrt] — Lean despliega la definición de sqrt dentro de la hipótesis, reemplazando el nombre por el cuerpo real de la función (let cand := ...; if ...). A partir de ahí puede razonar sobre la estructura del if.

Esto no modifica la spec — es una operación dentro de la demostración. rw le dice a Lean “mirá adentro de esa función para razonar sobre ella”.

¿Por qué spec-first y no al revés?

Existen dos enfoques para verificación formal. Este repo usa el primero por una razón práctica.

Spec-first (este repo)

Estándar → Spec (código) → Proof

Primero escribís la función tal cual la define el estándar (RFC, EIP). Después demostrás que es correcta. La spec tiene que coincidir exactamente con otras implementaciones de Ethereum para ser interoperable.

Proof-first (Coq extraction)

Teorema → extracción → Código

Primero definís la propiedad matemática, después extraés código automáticamente. El código es correcto por construcción, pero puede no coincidir con el estándar externo.

El motivo: las specs criptográficas de Ethereum ya están publicadas y otras implementaciones las siguen al pie de la letra. Si el código se derivara de un teorema, podría ser matemáticamente correcto pero producir resultados distintos a los de otros clientes — rompiendo la interoperabilidad de la red. Entonces la dirección es: escribir la spec exacta, y después demostrar que esa spec exacta es correcta.

Cómo se compila

El lakefile.lean define dos targets:

EthCryptographySpecs

  • precompileModules := true
  • Genera .c.o.export en .lake/build/ir/
  • Se linkea dentro de la extensión Python (el runtime de Lean, libleanshared, se enlaza dinámicamente)
  • Compilado con -fPIC, lo que hace falta para meterlo en una librería compartida (.so)

Proofs

  • precompileModules := false
  • Solo genera .olean: el resultado de revisar los teoremas, no es código
  • No se linkea en Python
  • Usa Mathlib v4.29.1, la biblioteca matemática de Lean
